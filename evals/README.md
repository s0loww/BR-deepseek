# Замеры

Проверки, которые нельзя свести к регексу и которые поэтому не живут в
`ci/check.py`: они требуют суждения модели, дают разброс между прогонами и
запускаются руками, а не на каждый коммит.

## `triggering/` — находится ли правило по формулировке задачи

**Что закрывает.** Ленивая загрузка стоит на том, что модель выберет нужное
правило по `description` из индекса в `AGENTS.md`. `ci/check.py` проверяет,
что правило существует и что на него ссылается индекс. Ни одна проверка не
показывает, что оно **находится**. Описание, мимо которого проходят, — это
правило, которого фактически нет, причём без единого сигнала: файл на месте,
проверки зелёные.

**Отличие от airules.** Там на задание отвечает агент сессии — и это честно,
потому что сессия и есть целевая среда. Здесь целевая модель другая, чем та,
что ведёт разработку, поэтому её надо звать явно: `ask.py` шлёт задание в
DeepSeek API и складывает ответ в `runs/`.

Через `kun run` прогнать не вышло: Kun держит ключ в зашифрованном
credentials-store, привязанном к своему data-dir, и ключ из конфига не
подхватывает, а рабочий data-dir занят запущенным GUI. Для этого замера
потеря невелика — задание чисто текстовое, инструменты не используются, и от
среды зависит только системный промпт.

```bash
python evals/triggering/run.py prompt > prompt.md          # задание глазами
python evals/triggering/ask.py runs/<дата>.json --runs 3 --effort high
python evals/triggering/run.py score runs/<дата>-1.json    # сверка
python evals/triggering/run.py bias                        # проверка на списывание
```

### Три прогона, а не один

Один прогон не отличает дефект описания от разброса модели. Замерено здесь же:
на неизменном контенте счёт был 16/17, 15/17 и 17/17, и **состав промахов
разошёлся** — один кейс промахнулся дважды, другой единожды. Устойчивый промах
и мигающий — разные вещи; чинить стоит первый.

### Проверка на списывание (`bias`)

Кейс, собранный из слов целевого описания, проверяет описание само против
себя и зелёный всегда — самый лёгкий способ получить бессмысленные сто
процентов. `bias` считает, сколько **отличительных** слов запрос делит с
описанием своей цели: слова, встречающиеся у четырёх и более правил,
отбрасываются как общедоменные. Три и больше — кейс под подозрением.

Проверка отработала на авторе прямо в этом прогоне: после первой правки
описания `delegation` счётчик `split-or-self` поднялся с 0 до 2 — в описание
уехали слова самого запроса («сделать самому»). Формулировку переписали от
тела правила, счётчик вернулся к 0, а триггеринг остался.

### Когда можно менять ожидание

Только следом за контентом. Промах показал, что правило лежит не там, где его
ищут → меняется описание или тело → и уже поэтому меняется ожидание. Если
контент не двигался, а `expect` изменился — это подгонка, и замер становится
декорацией.
