# Kun: развести сборку BR-deepseek и 1С-проект по разным папкам

## Для человека — прочитать до запуска

**Когда это нужно.** 1С-проект поставлен в ту же папку, где лежит клон
сборки. Работать это работает, но:

- `python ci/check.py` там всегда красный — 31 ошибка «правило оверлея
  отсутствует в Rule Index». Настоящую ошибку среди них не увидеть;
- `git pull` обновит правила в `overlays/1c/rules/`, а агент читает их копии в
  корневом `rules/` — обновления сборки до проекта молча не дойдут;
- рабочие файлы проекта (`AGENTS.md`, `.kun/`, `.dev.env`, исходники) лежат
  внутри чужого git-репозитория.

**Что получится.** Три папки:

| | что это | дальше |
| --- | --- | --- |
| **X** — текущая папка | как есть, ничего в ней не меняется | запасная копия; удалить — ваше решение, когда проект поработает из P |
| **B** — новая | чистый клон сборки | отсюда обновляться (`git pull`) и ставить |
| **P** — новая | папка 1С-проекта | эту папку открывать в Kun |

**Как запустить.**

1. В Kun открыть тред на папке X. Модель `deepseek-v4-pro`, усилие `high`.
2. Вставить в тред раздел «Задание агенту» ниже целиком.
3. Агент будет останавливаться после каждой фазы и спрашивать. Отвечать
   явно: «да, дальше» или что поменять.

Понадобятся Python и git. Скрипт `install/kun_split.py` агент возьмёт из
свежего клона сборки — отдельно ничего скачивать не нужно.

Если песочница Kun не даёт агенту писать вне папки X (при `workspace-write`
так и будет) — агент выдаст команды PowerShell, их надо запустить самому и
вставить вывод в тред.

## Задание агенту

### Контекст

Текущий воркспейс — папка **X**: это git-клон сборки BR-deepseek, в который
дополнительно поставлен 1С-проект (корневой `AGENTS.md`, правила оверлея в
`rules/`, `.kun/`, `tools/`, файлы проекта). Задача — получить отдельный
чистый клон сборки **B** и отдельную папку проекта **P**. Папка X остаётся
нетронутой.

Какой файл чей, определяет только скрипт `<B>\install\kun_split.py` —
сравнением содержимого с источником в сборке. Не классифицировать файлы
самостоятельно по именам.

### Жёсткие правила

1. **В X ничего не менять:** не удалять, не перемещать, не редактировать
   файлы; не запускать в X `git reset`, `git clean`, `git checkout`,
   `git stash`, `git pull`, `git commit`.
2. **Секреты не читать и не выводить:** `.dev.env`, `.env`, профили
   `agent-1c.json`. Скрипт сравнивает их по хешу и печатает только путь.
3. Пароли не спрашивать и не вводить. Настройки Kun — одобрение
   `.kun/project.json`, per-agent overrides — делает человек.
4. **Каждая фаза заканчивается остановкой:** короткий отчёт, вопрос, ожидание
   явного «да». Не объединять фазы.
5. Если команда требует записи вне X, а песочница не пускает — не обходить
   ограничение: выдать готовые команды PowerShell с подставленными путями и
   попросить человека запустить их и вставить вывод.
6. Код выхода скрипта: `0` — порядок, `1` — нужно решение человека, `2` —
   ошибка. На `1` и `2` — остановиться и показать вывод.

### Фаза 1. Пути и чистый клон сборки

Спросить у человека пути **B** (клон сборки) и **P** (проект). Обе папки —
новые или пустые, не внутри X и не внутри друг друга. Дождаться ответа.

```powershell
git -C "<X>" remote get-url origin
git clone "<origin>" "<B>"
python "<B>\ci\check.py"
python "<B>\ci\assemble.py" --check
```

Ожидается `OK: build is consistent` и код выхода 0 у `assemble.py`. Иначе —
**СТОП** и вывод человеку. Сравнить `<B>\VERSION` с `<X>\VERSION`.

**СТОП.**

### Фаза 2. Разведка X (только чтение)

```powershell
python "<B>\install\kun_split.py" inventory "<X>" --out "$env:TEMP\kun-split-inventory.json"
```

Показать человеку вывод скрипта как есть: сводку по категориям и списки.
Для файлов категории «файл сборки, изменён локально» дополнительно показать
`git -C "<X>" diff --stat` (статистику, без содержимого).

Если версия в B новее, чем в X, — сказать: заполненный `AGENTS.md` из X
собирался по старому шаблону, после переноса его разделы надо сверить с
`<B>\overlays\1c\templates\AGENTS.md`.

Спросить и дождаться ответа:

1. Если есть «файл сборки, изменён локально»: переносить эти правки в проект
   (`--with-build-edits`) или нет (`--skip-build-edits`, правки останутся
   только в X).
2. Если есть «игнорируется git — решить»: какие из них нужны проекту. Их
   пути пойдут в `--include`. Виртуальные окружения (`.venv`) и кэши не
   переносить.

**СТОП.**

### Фаза 3. Установка сборки в P

Открыть `<B>\overlays\1c\README.md`, раздел «Установка в проект», и выполнить
его PowerShell-блок с `$src = '<B>'` и `$dst = '<P>'`. Порядок копирования в
блоке важен (1С-роли после базовых) — не переставлять команды.

Контракт `AGENTS.md` ляжет с плейсхолдерами — это нормально, заполненный
перенесётся в фазе 4. Заполнять руками не нужно.

Проверить, что в P появились `AGENTS.md`, `rules\`, `.kun\agents\`,
`.kun\skills\`, `.kun\project.json`, `tools\`.

**СТОП.**

### Фаза 4. Перенос файлов проекта

Сначала план, без записи:

```powershell
python "<B>\install\kun_split.py" carry "<X>" "<P>" <флаг из ответа 1> <--include путь для каждого из ответа 2>
```

Показать план: сколько файлов копируется, что перезаписывается, есть ли
конфликты. Перезаписываться должны только заполненный `AGENTS.md`,
поставленные файлы, которые правили в проекте, и (если выбрано) изменённые
файлы сборки.

**СТОП.** После «да»:

```powershell
python "<B>\install\kun_split.py" carry "<X>" "<P>" <те же флаги> --apply --out "$env:TEMP\kun-split-carry.json"
```

Каждая строка записи должна иметь пометку `[сверено]`. Строка `КОНФЛИКТ`
означает, что в P уже лежит другой файл с тем же путём: не решать самому,
показать человеку.

**СТОП.**

### Фаза 5. Проверка проекта

```powershell
python "<B>\install\kun_split.py" verify "<P>" "<B>" --out "$env:TEMP\kun-split-verify.json"
Select-String -Path "<P>\AGENTS.md" -Pattern '\{\{'
```

Ожидается `OK: проект собран` и пустой вывод `Select-String`. Строка `info`
со списком файлов, отличающихся от сборки, — не ошибка: это правки проекта,
перенесённые в фазе 4; сверить, что список совпадает с тем, что переносили.

Итоговый отчёт человеку:

- пути B и P;
- что перенесено (число файлов по категориям) и что осталось только в X;
- результат `verify`;
- шаги из раздела «Дальше — руками в Kun».

**Конец задания.**

## Дальше — руками в Kun (человек)

1. Открыть **P** как воркспейс. Треды из X в P не переедут — это отдельный
   воркспейс.
2. **Settings → Agents → Project MCP & Skills** — одобрить
   `.kun/project.json` в P. Одобрение привязано к папке и хешу файла, из X
   оно не переносится. Одобрять, только если RLM поставлен; без RLM проект
   работает, просто без навигации по коду.
3. **Settings → Agents** — проверить, что включён «AGENTS.md instructions» и
   на месте per-agent overrides: `explorer`, `error-fixer`, `tester` →
   `deepseek-v4-flash`.
4. Новый тред в P: «какие правила у тебя загружены и откуда». Должен назвать
   контракт и индекс правил, а не пересказать их содержимое.
5. X в Kun больше не открывать. Удалить X — когда проект поработал из P и
   ничего не потерялось.

## Обновление сборки в будущем

1. `git -C "<B>" pull`, затем `python "<B>\ci\check.py"`.
2. Повторить копирование из README оверлея, **кроме** `AGENTS.md` и
   `.kun/project.json`: они заполнены под проект и затрутся шаблоном.
   Изменения шаблонов в новой версии перенести в них руками.
3. Файлы, которые в проекте правились сознательно (их список печатает
   `verify` строкой `info`), перед копированием сохранить и вернуть после.
4. `python "<B>\install\kun_split.py" verify "<P>" "<B>"` — зелёный.
5. Если `.kun/project.json` поменялся — одобрить его в Kun заново.
