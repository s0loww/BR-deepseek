# Правила обмена в КД 3.1 (EnterpriseData)

Как и в КД 2.0, правила живут **в справочниках ИБ КД**. Отличается результат:
КД 3.1 генерирует **модуль менеджера обмена** (общий модуль BSL для движка
`ОбменДаннымиXDTO`) и работает с **XDTO-пакетом / версией формата** (XSD), а не
выгружает XML-правила для «Универсального обмена». За КД 2.0 —
`rules/kd2-exchange-rules.md`.

**Транспорт вне этого правила.** Ниже — что делать в ИБ КД и почему; чем ты до
неё дотягиваешься, задаёт раздел `1C tooling` корневого контракта
(`AGENTS.md`; конкретные вызовы — `tooling-playbooks.md`).
Работать на тестовой копии.

## 1. Карта владения — отсюда все ошибки

| Справочник | Владелец | Иерарх. |
|---|---|---|
| `Конвертации` | нет (топ) | да |
| `СоставыКонвертаций` | `Конвертации` | нет |
| `ПравилаКонвертацииОбъектов` (ПКО) | **нет (топ)** | **нет** |
| `ПравилаКонвертацииСвойств` (ПКС) | **ПКО** | да |
| `ПравилаОбработкиДанных` (ПОД) | **нет (топ)** | нет |
| `ПравилаКонвертацииПредопределенныхДанных` (ПКПД) | **нет (топ)** | нет |
| `Конфигурации` | нет (топ) | нет |
| `Релизы` | нет (топ) | да |
| `Объекты` | **`Релизы`** | да |
| `Свойства`, `Значения` | `Объекты` | да |
| `ВерсииФормата` | нет (топ) | да |
| `ОбъектыФормата` | `ВерсииФормата` | да |
| `СвойстваФормата` | `ОбъектыФормата` | да |
| `ТипыФормата` | `ВерсииФормата` | нет |
| `ЗначенияФормата` | `ОбъектыФормата`, `СвойстваФормата` | нет |

Три следствия, каждое из которых ломает перенесённые из КД 2.0 привычки:

1. **ПКО/ПОД/ПКПД — топ-уровневые, без Владельца.** С конкретной Конвертацией
   они связываются **записью `СоставыКонвертаций`** (Владелец = Конвертации,
   реквизит `ЭлементКонвертации` — ссылка на правило). Создать ПКО и ждать, что
   оно попадёт в конвертацию, — не сработает. У ПОД синоним стандартного
   реквизита Владелец остался («Конвертация»), но подчинённости нет — рудимент.
2. **У ПКО нет реквизита `Наименование`.** Идентификатор — `Код` (строка 50),
   искать через `НайтиПоКоду`. И ПКО **не иерархичен**: `ЭтоГруппа` нет.
   Иерархичен ПКС.
3. **ПКС — справочник, а не регистр сведений.** Обращение
   `Метаданные.РегистрыСведений.ПравилаКонвертацииСвойств` падает; правильно
   `Метаданные.Справочники.ПравилаКонвертацииСвойств`.

## 2. Без Релиза привязывать правила не к чему

Теневая модель метаданных наполняется загрузкой структуры конфигурации
(обработка `ЗагрузкаСтруктурыКонфигурацииИзФайловXML`). Пока её не было,
`Объекты` и `Свойства` пусты.

```bsl
// 0 -> структура конфигурации не загружена, дальше идти бессмысленно
ВЫБРАТЬ КОЛИЧЕСТВО(*) ИЗ Справочник.Релизы
```

Реквизиты Конвертации `Конфигурация` и `КонфигурацияКорреспондент` ссылаются
именно на **Релизы**, а не на `Конфигурации`: версии живут в Релизах,
`Конфигурации` — топ-контейнер.

Загрузка большой конфигурации — десятки тысяч объектов и десятки минут. Она
занимает сеанс целиком: запускать фоном и опрашивать готовность, а не ждать
синхронного ответа. Обрыв по таймауту у запускающего вызова — не отказ, работа
продолжается в своём сеансе.

**Загрузчик удаляет поданные файлы.** И загрузка структуры, и загрузка формата в
конце делают `УдалитьФайлы(...)` по каждому поданному файлу. Подавать всегда
**временную копию** XSD и `.mdo`, а не оригиналы из рабочего каталога или EDT —
иначе останешься без исходников.

## 3. Пара ПКО на объект

Штатный паттерн заполнения — **два ПКО на объект**: `<Объект>_Отправка` и
`<Объект>_Получение`, различаются флагами `ИспользоватьДляОтправки` /
`ИспользоватьДляПолучения`.

Ключевые реквизиты ПКО:

- `ОбъектКонфигурации`, `ОбъектКонфигурацииКорреспондент` — ссылки на `Объекты`;
- `ОбъектФормата` — **строка** (имя объекта формата), не ссылка;
- `ВариантИдентификации` — `ПоУникальномуИдентификатору` / `ПоПолямПоиска` /
  `СначалаПоУникальномуИдентификаторуПотомПоПолямПоиска`;
- `ГруппаПравил` — строка, не ссылка (справочника `ГруппыПравил` нет);
- `АлгоритмПриОтправкеДанных` / `АлгоритмПриПолученииДанных` — тексты BSL,
  которые в сгенерированном модуле менеджера станут процедурами.

Табличные части: `ИдентификацияПоПолямПоиска`,
`НастройкаВариантовПоискаОбъектовXML`, `Теги`.

ПКС связывает свойство конфигурации (`СвойствоКонфигурации`, ссылка) со
свойством формата (`СвойствоФормата`, **строка**). Для ссылочного свойства
`ПравилоКонвертацииСвойства` — тоже **строка** (имя ПКО), а не ссылка. Для
нестандартного заполнения — алгоритм плюс флаг
`ИспользуетсяАлгоритмКонвертации`; без флага алгоритм не включится.

## 4. Демо-база как эталон

Типовая поставка КД 3.1 содержит готовую конвертацию — сотни ПКО и тысячи ПКС.
Структура метаданных у демо и рабочей ИБ одна и та же, поэтому перед созданием
своего правила дешевле снять образец аналогичного из демо, чем угадывать:
как заполнены `Код`, `ОбъектКонфигурации`/`ОбъектФормата`, как оформлены прямые
ПКС против алгоритмических, как связаны ссылочные.

## 5. Порядок работы

Шаги ниже строго упорядочены: каждый следующий опирается на данные предыдущего,
и попытка перепрыгнуть даёт пустые справочники, а не ошибку.

1. **Загрузить структуру конфигурации** — создаётся Релиз, наполняются
   `Объекты`/`Свойства` (§2). Загрузчик понимает и исходники EDT напрямую.
2. **Привязать Релиз к Конвертации**: `Конфигурация` и
   `КонфигурацияКорреспондент` — ссылки на загруженный Релиз. Для
   двустороннего обмена одной и той же конфигурации это **один и тот же** Релиз.
3. **Подготовить версии формата** — базовую и своё расширение (§7).
4. **Наполнить правила**: ПКО (объект конфигурации ↔ объект формата), ПКС,
   ПОД (точки выгрузки), ПКПД (предопределённые и перечисления). Простые
   правила создаются как элементы справочников; нестандартная логика — в
   алгоритмах ПКО.
5. **Сгенерировать артефакты**: модуль менеджера обмена и XSD версии формата.
6. **Перенести в расширение приёмника**: XSD → `XDTOPackage`, BSL →
   `CommonModule`.
7. **Зарегистрировать расширение формата** у приёмника (§7).

## 6. Обработчики в сгенерированном менеджере

Алгоритмы ПКО становятся процедурами модуля менеджера:

- отправка (ИБ → XDTO): `ПКО_<Имя>_ПриОтправкеДанных(ДанныеИБ, ДанныеXDTO,
  КомпонентыОбмена, СтекВыгрузки)` — заполняется `ДанныеXDTO` из `ДанныеИБ`,
  включая поля расширения;
- получение (XDTO → ИБ): `ПриКонвертацииДанныхXDTO(ДанныеXDTO,
  ПолученныеДанные, КонвертацияСвойств, КомпонентыОбмена)`.

Ссылочное свойство с динамическим выбором правила передаётся структурой:

```bsl
Новый Структура("Значение, ИмяПКО", Ссылка, "<ИмяПКО>")
```

Табличная часть через алгоритм — собрать таблицу значений и положить её
`ДанныеXDTO.Вставить("<ИмяТЧ>", Таб)`.

## 7. Расширение формата и его регистрация

Состав формата хранится **не в табличных частях**, а в цепочке подчинённых
справочников (§1): объекты и свойства расширения создаются элементами
`ОбъектыФормата`/`СвойстваФормата` под записью `ВерсииФормата` с
`Расширение = Истина` и собственным `ПространствоИмен`. К Конвертации версии
формата привязываются табличной частью `Конвертации.ВерсииФормата`.

На стороне приёмника расширение объявляется перехватом типовой процедуры:

```bsl
&После("ПриПолученииДоступныхРасширенийФормата")
Процедура <Преф>_ПриПолученииДоступныхРасширенийФормата(РасширенияФормата)
    РасширенияФормата.Вставить("<URI расширения>", "<версия базового формата>");
КонецПроцедуры
```

Перехват — **по имени процедуры**, а не по строке кода: так он переживёт
обновление типовой.

**Эволюция схемы.** Новые поля расширения добавлять необязательными. Изменение
XDTO-пакета на стороне приёмника требует реструктуризации ИБ — это плановое
обновление, а не горячая правка.

## 8. Как это выглядит целиком

Один объект от загрузки структуры до процедуры в менеджере — чтобы шаги §5 не
приходилось склеивать в голове. Имена ниже — форма, а не значения: подставляй
свои.

| Звено | Что это в вашем контуре |
|---|---|
| Конвертация | `РасширениеEnterpriseData` — пара обмена, к ней привязаны Релиз и версии формата |
| Базовый формат | EnterpriseData нужной версии, элемент `ВерсииФормата` |
| Расширение формата | второй элемент `ВерсииФормата`, `Расширение = Истина`, свой `ПространствоИмен` вида `http://<домен-владельца-формата>/<расширение>/1.0` |
| Объект формата | `ОбъектыФормата` под записью расширения; свойства — `СвойстваФормата` под объектом |
| ПКО | пара `Номенклатура_Отправка` / `Номенклатура_Получение`, `ОбъектКонфигурации` — ссылка, `ОбъектФормата` — строка |
| ПКС | `СвойствоКонфигурации` (ссылка) ↔ `СвойствоФормата` (строка) |
| Артефакт 1 | `XDTOPackage.<Преф>_РасширениеФормата_1_0` в расширении приёмника |
| Артефакт 2 | `CommonModule.<Преф>_МенеджерОбменаРасширение` — сгенерированный модуль |
| Регистрация | `&После("ПриПолученииДоступныхРасширенийФормата")` в `ОбменДаннымиПереопределяемый` (§7) |

Сквозная нить: ПКО `Номенклатура_Отправка` с алгоритмом
`АлгоритмПриОтправкеДанных` превращается при генерации в процедуру
`ПКО_Номенклатура_Отправка_ПриОтправкеДанных(ДанныеИБ, ДанныеXDTO, …)` внутри
`CommonModule.<Преф>_МенеджерОбменаРасширение`. Не найдя своей процедуры в
сгенерированном модуле, ищи ПКО с тем же именем и смотри, заполнен ли у него
алгоритм и стоит ли `ВыгружатьВМодульМенеджера`.

**Границы примера.** Имена контура, реальный URI пространства имён, список
переносимых объектов и контракт обмена — это **проектный** слой: они живут в
памяти цели и в её документах, а не здесь. В правиле остаётся форма связей,
которая одинакова у всех, кто делает расширение формата.

## 9. Имена, которые принято путать

**Значения перечислений короткие**, и «логичные» длинные варианты не
существуют:

| Перечисление | Значения |
|---|---|
| `ТипыКонвертаций` | `XML`, `XDTO` (не `ФорматXDTO`) |
| `ВариантыМоделейОбмена` | `ПакетнаяМодель`, `ОбъектнаяМодель`, `КомбинированнаяМодель` |
| `ВариантыИдентификацииОбъектов` | `ПоУникальномуИдентификатору`, `ПоПолямПоиска`, `СначалаПоУникальномуИдентификаторуПотомПоПолямПоиска` |
| `СостоянияПравил` | `Черновик`, `ВРаботе`, `НаТестировании`, `Готово`, `Архив` |

Перечислений `ИнтерфейсыКонвертации` и `ВариантыИдентификацииОбъектовПКО` нет —
их «очевидные» имена придуманы, а не выведены из конфигурации.

**Имена обработок сверять с фактическими** в конкретной сборке: генерация
модуля — `ВыгрузкаМодуля`, загрузка структуры —
`ЗагрузкаСтруктурыКонфигурацииИзФайловXML`, редактор правил —
`НастройкаПравилОбмена`. Имён вида `ВыгрузкаПравил` или
`ПомощникСозданияФорматаXDTO` в ней не существует — проверять по
`Метаданные.Обработки` перед вызовом.

**`ВерсияФорматаМенеджера` — короткий реквизит.** Строка `"1.10"` молча
обрезается до `"1."`. Полная версия хранится в URI пространства имён версии
формата; после записи короткого реквизита сверять, что записалось.

## 10. Мелочи, на которых спотыкаются

- **`Справочники.X.Количество()` не существует** — падает «Метод объекта не
  обнаружен». Считать запросом: `ВЫБРАТЬ КОЛИЧЕСТВО(*) ИЗ Справочник.X`.
- **«Поле объекта не обнаружено» при обращении к метаданным** — почти всегда не
  та коллекция. ПКС лежит в `Метаданные.Справочники`, а не в
  `Метаданные.РегистрыСведений` (§1); имя сверять по списку коллекции.
- **Удалять правила `Удалить()` не стоит** — в обычных формах вызов виснет на
  модальном подтверждении. Помечать на удаление, физически убирать через UI КД.
