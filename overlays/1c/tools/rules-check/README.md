# rules-check: правила оверлея, ставшие исполняемыми

Правила дистрибутива до сих пор были текстом, который агент мог прочитать, а мог
и не прочитать. Ту их часть, что разрешима механически, читать не обязательно —
её можно проверять, бесплатно и до того, как что-либо попадёт в контекст.

```bash
python rules_check.py --scope staged                    # гейт перед коммитом
python rules_check.py --scope path --path src/CommonModules
python rules_check.py --scope diff --base main --json
python rules_check.py --list-rules
```

Два входа, одна реализация: pre-commit (детерминированно, ноль токенов) и
ручной запуск с `--json` для любого другого вызывающего (CI, агент, скрипт).

Только стандартная библиотека и никаких внешних зависимостей: чекер ездит
вместе с правилами, и ставиться они должны независимо.

## Правила

| id | важность | из чего |
| --- | --- | --- |
| `ext-continue-outside-instead` | error | `ПродолжитьВызов()` компилируется только внутри `&Вместо` |
| `ext-instead-without-continue` | warning | `&Вместо` без `ПродолжитьВызов()` — оригинал не выполнится |
| `ext-designer-markers` | error | `#Вставка`/`#Удаление` в перехватчике: платформа **молча** перестаёт применять модуль, а деплой проходит |
| `log-level-slot` | error | 2-й аргумент `ЗаписьЖурналаРегистрации` — Уровень |
| `log-transaction-slot` | error | 6-й аргумент — РежимТранзакции; Структура идёт 4-м |
| `form-reserved-name` | error | локальная переменная в модуле формы названа как свойство элемента |
| `query-in-loop` | error | запрос выполняется в цикле |

Источник каждого правила указан в `rules.py` и в выводе `--json`. **Когда
чекер расходится с текстом правила — прав текст, а чекер сломан.**

## Что сюда не попадает

Правила делятся на три класса, и смешивать их в одном инструменте — ошибка:

- **разрешимые механически** — здесь;
- **требующие навигации** («нет ли уже такого в БСП», «не сломает ли
  переопределение базу») — решаются через RLM или руками агента, не регуляркой;
- **судейские** («держи обработчик тонким») — остаются агенту.

## Точность важнее полноты

Чекер, который врёт, выключают — и вместе с ним перестают действовать правила,
которые он ловил верно. Поэтому принцип такой: **сообщать только то, что
доказуемо из исходника.**

Первый прогон по реальной конфигурации (446 модулей) дал 143 находки, и
выборочная проверка нашла две ложные — обе в логгирующих правилах:

```bsl
?(Успешно, УровеньЖурналаРегистрации.Информация, УровеньЖурналаРегистрации.Ошибка)
ПараметрыЗаписи.РежимТранзакции
```

Оба фрагмента корректны, но не совпадают с шаблоном «литерал перечисления».
Правила требовали доказать правильность — а надо было доказывать неправильность.
Переписано: слот помечается ошибочным, только если он строковый литерал, число
или конструктор `Новый`. Переменную, свойство или тернарку из исходника
рассудить нельзя, поэтому о них молчим. Осталось 132 находки, обе ложные формы
лежат в `fixtures/clean/logging.bsl` — прибиты регрессией навсегда.

Подавить осознанное исключение: `airules:allow <rule-id>` в той же строке.

## Сканер

`bsl.py` — не парсер. Он отвечает на четыре вопроса, которых регулярка сама не
осилит: где комментарии и строковые литералы (чтобы шаблон не срабатывал внутри
сообщения), какой процедуре принадлежит строка и какие у процедуры аннотации,
находится ли строка внутри цикла, и каковы позиционные аргументы вызова с учётом
вложенности.

Сквозной принцип: **решение принимается по «забланкованному» тексту, показывается
оригинал.** В забланкованном строковые литералы — пробелы, поэтому литерал не
может сойти за ссылку на перечисление только потому, что так написан.

Пропущенные позиционные аргументы (`Ф(А, , Б)`) в 1С осмысленны и сохраняются:
без этого слоты сдвигаются и правила о 2-м и 6-м аргументе начинают врать.

## Гейт

```bash
python test_rules_check.py           # проверка
python test_rules_check.py --update  # перезаписать эталон после разбора
```

Две стороны, и первая важнее: `fixtures/clean/` обязан молчать (точность),
`fixtures/dirty/` — выдать ровно записанный набор (полнота). Каждая ложная
находка с реального корпуса переезжает в `clean/` и больше не возвращается.
Гейт заодно проверяет сам сканер: бланкование строк и комментариев, удвоенную
кавычку внутри литерала, сохранение пропущенных слотов, непротекание аннотаций
на следующую процедуру и работу маркера подавления.

## Подключение из CI / скрипта

```bash
python rules-check/rules_check.py --scope staged --json
```

Вызов с `--json` отдаёт нарушения обычными записями: `name` — id правила,
`owner` — важность, `loc` — файл и строка, `text` — сообщение и
файл-источник правила. Разложить их в собственный формат — дело вызывающей
стороны (CI-джоб, pre-commit хук, агент).
