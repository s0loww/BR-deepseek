# Разбор технологического журнала (ТЖ)

Скрипт `tools/tj.py` (рядом с этим файлом) читает каталог журнала, `.log`,
`.zip` или `.7z` потоком и печатает сводки. Только чтение, только стандартная
библиотека Python.

## Правило данных — до первой команды

ТЖ содержит тексты запросов с параметрами, имена пользователей и компьютеров,
адреса серверов, значения ключей блокировок. Всё, что попало в контекст,
уходит провайдеру модели.

- **Не читать сырые `.log` в контекст** — ни `read`, ни `grep` по журналу.
  Только через `tj.py`: по умолчанию он печатает агрегаты без этих полей.
- `--sql` (нормализованный текст запроса без литералов) и `--descr` (начало
  описания ошибки) добавляют данные — только если пользователь согласился.
- Журнал не распаковывать: архив читается потоком.

## Порядок

1. **Вход.** Путь к журналу и период жалобы — у пользователя. Большой
   журнал сразу сузить по часам: `--from ГГММДДЧЧ --to ГГММДДЧЧ`
   (часы берутся из имён файлов). В одном каталоге `rphost_*` бывают
   несколько баз — `--infobase` по `p:processName`.

2. **`inventory` — всегда первым.** Он показывает, какие события журнал
   записал и на какие вопросы по ним можно ответить.

   ```
   python tools/tj.py inventory <путь>
   ```

   Если долгих вызовов в ответе «нет» (в `logcfg` не включены `CALL` /
   `SCALL` и события запросов) — **так и сказать**: по этому журналу долгие
   вызовы не найти. Выдать рецепт `docs/logcfg.md` и попросить снять журнал
   заново в часы жалоб. Не подменять вопрос разбором того, что есть: захваты
   `TLOCK` без ожидания — не причина медленной работы.

3. **Вопрос → команда.**

   | Вопрос | Команда |
   | --- | --- |
   | Какие серверные вызовы долгие | `top <путь> --event CALL,SCALL --by context` (или `--by module`) |
   | Какие запросы долгие | `top <путь> --event DBMSSQL,SDBL --by sql`, затем `--by context` — откуда они выполняются |
   | Самые долгие одиночные случаи | `slowest <путь> --event DBMSSQL -n 20` |
   | Когда тормозит | `top <путь> --by hour` |
   | Конфликты блокировок | `locks <путь>` |
   | Ошибки | `errors <путь>` |

   `--by context` — самый внутренний кадр стека (`Модуль : строка :
   оператор`), `--by context-first` — точка входа, `--by stack` — весь стек.
   `--sort max` — по самому долгому случаю вместо суммы. `--min-ms` отсекает
   короткие события.

4. **Место кода → код.** Кадр `ОбщийМодуль.X.Модуль : 120 : …` открывается
   через RLM: `find_module`, затем `read_procedure` вокруг строки
   (`rules/tooling-playbooks.md`, раздел Performance). Сверить с
   `rules/anti-patterns.md`; конфликт блокировок — с
   `rules/locks-and-transactions.md`.

5. **Отчёт.** Факт (цифры сводки, период, база, какие события журнал вообще
   писал) → гипотеза → чем проверить. Сводку сохранить для перепроверки:
   `--out <каталог логов проекта>/tj-<команда>.json`.

## Что знать о данных

- Длительность в 8.3 — микросекунды (6 знаков дроби во времени), в 8.2 —
  десятитысячные секунды (4 знака). Скрипт определяет сам и пишет единицу в
  `inventory`.
- Событие может быть записано без свойств (`…,EXCP,2` и конец строки) —
  так бывает, когда `logcfg` не просит свойств для этого события. Места и
  причины у такого события нет; `errors` говорит об этом отдельно.
- Один каталог `rphost_*` обслуживает несколько баз: разбирать по одной
  (`--infobase`), иначе чужая нагрузка смешается со своей.
- `TLOCK` пишется на каждый захват. Конфликт — только `TLOCK` с непустым
  `WaitConnections`, `TTIMEOUT` и `TDEADLOCK`.
- `--by module` для `CALL` — эвристика по свойствам `Module` / `Method`
  или `IName` / `MName`; где их нет, группировка падает на Context.
- Запросы группируются по отпечатку `q:…` текста без литералов, чисел,
  параметров и номеров временных таблиц.

## Коды выхода

`0` — сводка построена; `1` — под запрос нет событий (журнал их не
записывал или фильтры всё отсекли); `2` — ошибка входа; `3` — сводка
построена, но часть файлов не прочитана (перечислены в «Замечаниях»).

## Проверка скрипта

`python tools/test_tj.py` — синтетические фикстуры с ловушками формата и
проверка, что по умолчанию в выводе нет пользователей, хостов и данных.
