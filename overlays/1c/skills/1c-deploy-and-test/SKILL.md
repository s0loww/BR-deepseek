# Деплой и проверка (1С)

Конкретные пути, имена баз, версию платформы и имя расширения даёт раздел
`## 1C tooling` корневого контракта проекта (`AGENTS.md`). Здесь — порядок и
жёсткие правила, одинаковые для любого 1С-проекта.

## Жёсткие правила

- **Определи, что лежит в каталоге исходников: конфигурация или расширение**
  (`Configuration.xml` → `Properties/Name`; сверься с `AGENTS.md`). Если это
  РАСШИРЕНИЕ — каждый `1cv8 DESIGNER /LoadConfigFromFiles` и `/UpdateDBCfg`
  ОБЯЗАН нести `-Extension <ИмяРасширения>`: голая команда без него
  **перезапишет основную конфигурацию базы**. Сомневаешься — не запускай сырые
  команды, используй проектный скрипт деплоя.
- **Деплой только проектным инструментом** (скрипт деплоя, указанный в
  `AGENTS.md` → `## 1C tooling`), не сырыми командами платформы: скрипт несёт
  правильные флаги, режимы Load/Update и редакцию пароля в логах.
- **Целевая база — тестовая**, из env-профиля проекта (секция указана в
  `AGENTS.md` → `## 1C tooling`). Боевые базы не трогать без явного указания
  пользователя. Креды не выводить ни в stdout, ни в логи, ни в отчёты;
  env-файл не редактировать.
- Версия платформы — фиксированная в `AGENTS.md` → `## 1C tooling`; не
  подставлять «какая найдётся».

## Порядок

1. **Деплой** проектным скриптом → проверить exit-коды/лог (успех загрузки И
   успех обновления структуры БД). Изменения структуры (новые ТЧ/реквизиты)
   требуют монопольного обновления вместо динамического.
2. **Статическая проверка** (BSL LS / `tools/agent-1c` analyze, если
   настроен): у зрелых проектов есть baseline диагностик — **гейтить только
   новые** относительно baseline, старые не чинить без отдельной задачи.
3. **Проверка после деплоя** — каналами, которые реально настроены в проекте
   (см. `AGENTS.md` → `## 1C tooling`), в порядке дешевизны:
   - смоук клиентом: поднять клиент на тестовой ИБ, дождаться отклика; после
     проверки клиент закрыть (открытый клиент со старой версией расширения
     ломает последующие COM-подключения к файловой базе);
   - проверка данных/движений регистров COM-скриптами по контракту
     `tools/com-tools` (изменяющие скрипты — только с согласия пользователя и
     только в копиях);
   - сценарные прогоны (Vanessa/vrunner через `tools/agent-1c`), если suite
     настроен — для 1С-контура это и есть «affected automated tests» гейта D
     `rules/verification-matrix.md`;
   - MCP-доступ к базе, если развёрнут на тестовой ИБ.
   Каналы, которых в проекте нет (веб-публикация, раннеры), — не выдумывать и
   не имитировать: явно сказать, что канал не развёрнут.

## Отчёт

Exit-коды деплоя · новые Error статпроверки · результат каждой проверки
PASS/FAIL с доказательством (лог/запрос/скриншот) · точные тексты ошибок.
